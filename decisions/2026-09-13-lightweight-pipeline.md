# 決定: パイロット用パイプラインは「main 直 push → ビルド → 公開」の最軽量にする

日付: 2026-09-13

## 決めたこと

- 作品 repo に PR、自動マージ(merge-guard)、ルールセット、必須チェックを**置かない**。AI も人間も main に直接 push する。
- 流れは `push to main → Actions でビルド → Pages 公開(+ 必要なら itch.io)` の 1 本。CI は「ビルドが通る」だけ。型検査・単体テスト・E2E はパイロットでは走らせない(作り込み段階で足す)。
- Yasu 型(PR → Guard → bot マージ → 認可ゲート → 公開)は、複数人・製品化・秘密情報を扱う段階の選択肢として ai-dev-infra に残しておく。今は使わない。

## 根拠

- ユーザー判断: 個人ゲーム制作で誤 push の実害はない。重さの原因はこの安全弁の集まりだった。
- ルールセット無しでできなくなる自動化は無い。Pages 公開も itch.io 公開も Actions だけで完結する。ルールセットは「人間やAIの誤操作を止める」ためだけの機能。

## 影響

- 01: 雛形の `.github/workflows/` は `build-and-deploy.yml` 1 本(+ itch 公開の任意ジョブ)。
- 08: ai-dev-infra の再利用ワークフローは deploy-pages / publish-itch の「ゲート無し版」を新設して呼ぶか、雛形に直書きするか。直書きの方が軽い。要検討。
- 11: 誤 push の復旧は `git revert` で足りる。
