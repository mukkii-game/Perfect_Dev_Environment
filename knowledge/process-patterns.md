# 作り方の型(引くためのもの)

過去の自分の作品・企画から回収した「進め方」の型。コードやツールではなく手順。
AI に任せる範囲と人間が決める範囲の切り分けが共通のテーマ。

最終確認: 2026-10-01(出所は自分の repo。非公開のものは repo 名を伏せる)

## 1. 企画を多角的に出して、軸ごとの審査役で絞る(非公開の企画 repo より)

1 日 1 本の「何を作るか」や、作り込む作品のコア選びに使える。

1. **候補を 10 前後、わざと違う切り口で出す**。1 つは必ず「ワイルドカード」(どれにも当てはまらない案)
2. **審査役を軸ごとに分ける**。1 人が全部を見ない。例: 手触り / 新しさ / 原作・目標らしさ / 読みやすさ /
   **反対役(レッドチーム。粗を探すだけ)** / 全体の統一感
3. 各審査は**点数の表 + 一言 + 欠点**を必ず書く。良い点だけの審査は無効
4. 点数を合わせて**上位 3 案だけを磨く**。残りは捨てずに「候補」フォルダに置いておく
5. 最後に人間が 1 つ選ぶ

**効く理由**: AI は 1 回の生成だと無難な案に寄る。切り口を強制し、審査を分けると、
「面白いが欠点もある」案が埋もれずに残る。反対役がいると褒め合いにならない。

## 2. 人間確認の段階を固定する(非公開のアプリ repo より)

AI が大量に作ったもの(教材・データ・素材・文面)を扱う時の型。

- 状態を段階で持つ: **下書き → 検証中 → 人間確認済み → 公開**
- **AI が進めてよいのは「検証中」まで**。「人間確認済み」への変更と公開判断は人間だけ
- 人間のレビューは **keep / rewrite / reject / defer の 4 択**で記録する(迷ったら defer)
- 大量レビューは、対象を固定した一覧(表)で往復し、元データは書き換えない

**効く理由**: AI が「確認済み」と書けてしまうと、誰も見ていないものが公開される。
段階を固定すると、人間が見るべきものだけが手元に残る。
→ 毎朝のニュースレター・週 1 の取捨・公開キットの「未投稿 / 投稿済み / 公開確認済み」も同じ考え方。

## 3. 調査は決まった書式で書き、スクリプトで表にする(非公開の企画 repo より)

- 参考作の調査を、見出しの書式を固定して書く。例:
  `### 作品名(年, 開発元, 機種)|関連度: X|対応目標: G1,G3`
- 小さなスクリプトで全部を 1 枚の表(CSV)に集める
- **事実と推測を分け、未確認の事実には「(未確認)」を付ける**

**効く理由**: AI に調べさせた結果を、あとで並べ替え・絞り込みできる。書式がばらつくと集計できない。

## 4. 開発記録は 5 項目で書く(NeoSoukoban より)

版ごとに: **症状 → 原因 → 修正 → どう確かめたか → 実機で未確認な点**

**効く理由**: 後からノウハウとして回収できる。2026-10-01 の過去作の洗い出しで、
この形で書かれた記録だけがそのまま持ち出せた。
→ 雛形の `HANDOFF.md` の「ハマったこと」欄をこの形にする(次の改善候補)。
