# 作り方の型(引くためのもの)

過去の自分の作品・企画から回収した「進め方」の型。コードやツールではなく手順。
AI に任せる範囲と人間が決める範囲の切り分けが共通のテーマ。

最終確認: 2026-10-08(1〜4 は自分の repo 由来。非公開のものは repo 名を伏せる。5〜7 は外の記事由来で、週 1 取捨 10/8 で採用)

## 1. 企画を多角的に出して、軸ごとの審査役で絞る(非公開の企画 repo より)

1 日 1 本の「何を作るか」や、作り込む作品のコア選びに使える。

1. **候補を 10 前後、わざと違う切り口で出す**。1 つは必ず「ワイルドカード」(どれにも当てはまらない案)
2. **審査役を軸ごとに分ける**。1 人が全部を見ない。例: 手触り / 新しさ / 原作・目標らしさ / 読みやすさ /
   **反対役(レッドチーム。粗を探すだけ)** / 全体の統一感
3. 各審査は**点数の表 + 一言 + 欠点**を必ず書く。良い点だけの審査は無効
4. 点数を合わせて**上位 3 案だけを磨く**。残りは捨てずに「候補」フォルダに置いておく
5. 最後に人間が 1 つ選ぶ

**効く理由**: AI は 1 回の生成だと無難な案に寄る。切り口を強制し、審査を分けると、
「面白いが欠点もある」案が埋もれずに残る。反対役がいると褒め合いにならない。

## 2. 人間確認の段階を固定する(非公開のアプリ repo より)

AI が大量に作ったもの(教材・データ・素材・文面)を扱う時の型。

- 状態を段階で持つ: **下書き → 検証中 → 人間確認済み → 公開**
- **AI が進めてよいのは「検証中」まで**。「人間確認済み」への変更と公開判断は人間だけ
- 人間のレビューは **keep / rewrite / reject / defer の 4 択**で記録する(迷ったら defer)
- 大量レビューは、対象を固定した一覧(表)で往復し、元データは書き換えない

**効く理由**: AI が「確認済み」と書けてしまうと、誰も見ていないものが公開される。
段階を固定すると、人間が見るべきものだけが手元に残る。
→ 毎朝のニュースレター・週 1 の取捨・公開キットの「未投稿 / 投稿済み / 公開確認済み」も同じ考え方。

## 3. 調査は決まった書式で書き、スクリプトで表にする(非公開の企画 repo より)

- 参考作の調査を、見出しの書式を固定して書く。例:
  `### 作品名(年, 開発元, 機種)|関連度: X|対応目標: G1,G3`
- 小さなスクリプトで全部を 1 枚の表(CSV)に集める
- **事実と推測を分け、未確認の事実には「(未確認)」を付ける**

**効く理由**: AI に調べさせた結果を、あとで並べ替え・絞り込みできる。書式がばらつくと集計できない。

## 4. 開発記録は 5 項目で書く(NeoSoukoban より)

版ごとに: **症状 → 原因 → 修正 → どう確かめたか → 実機で未確認な点**

**効く理由**: 後からノウハウとして回収できる。2026-10-01 の過去作の洗い出しで、
この形で書かれた記録だけがそのまま持ち出せた。
→ 雛形の `HANDOFF.md` の「ハマったこと」欄をこの形にする(次の改善候補)。

## 5. 頼むたびに書く 4 つの決まり(rewind の UE × Claude Code 講座より)

毎回のプロンプトに次の 4 つを入れる:
1. **「完了」の定義**を書く(何ができたら終わりか)
2. **変えてはいけない所**を書く
3. **触ったものの一覧**を出させる
4. **黙って回避させない**。できない時は止まって報告させる

あわせて: 1 機能 = 1 プロンプトで積む(箱だけの仮レベル → ルール → 敵 1 体 → 体力 → 攻撃 → 見た目)。
始める前に毎回コミット。権限確認は切らない。プレイ中・コンパイル中に頼まない。

**効く理由**: AI は「終わり」が曖昧だと勝手に広げ、できない所を黙って別の形で埋める。4 つで範囲と報告を固定できる。
エンジンに依存しない(Godot・Web でもそのまま使える)。記事自身の注意: 知らない部分を埋める道具ではなく、頭にある作業を速くする道具。
出典: https://x.com/rewind02/status/2107086047985258639 (2026-10-05、確認 2026-10-08)

## 6. AI にテストプレイさせる設計(giginet『トルネコの大冒険』を 134 回遊ばせた記録より)

- **意味単位の操作 → 入力列**: 「3 番目のアイテムを使う」「西の出口まで進む」を受け取り、決まった入力に変換する層を挟む(ボタン 1 つずつだとトークンが足りない)
- **状態は画面でなく直接読む**: 体力・満腹度・持ち物・周辺マップを RAM から。見えないはずの情報は落とす(フェア)
- **禁止はプロンプトでなく仕組み側で拒否**する(効果のない操作をコマンドごと拒否)
- **死ぬたびに仕組みを直す**。攻略の気づきは AI 自身に手順書(`tactics.md`)へ書き足させる
- 結果: 134 回目・約 12.5 時間で最深部。AI は保守的すぎてアイテムを使い切りがち →「リスク許容度を上げる」で改善。完全自走ではなく、人間が管理役

**効く理由**: 自作ゲームなら RAM 読みは不要で、状態を文字で返す関数と「意味単位の操作」API を最初から持てる。
erukiti の 4 つの型(決定論・表示とロジックの分離・bot・リプレイ、AI知見 10/6)と組み合わせると、AI が自分で遊んで検証できる。
注意: 時間とトークンはかなりかかる(2〜3 週間の検証)。
- **文章が主役のゲームは、年代・立場の違うペルソナ(サブエージェント 4 人)に通読させる**(game-creator-life 2026-10-16、30 回): sim の全文をテキストに書き出して読ませ、「笑った行・滑った行・時代考証・アイデア 5 つ」と点数を返させる。**1 回目と「3 回続けて遊んだ時」を別に採点**させると、初回 7 点でも続けると 4〜5 点に落ち、言い回しの被り・身の上とのずれ(服役中に作品を出す等)が一気に出る。
出典: https://giginet.hateblo.jp/entry/2026/09/22/114642 (確認 2026-10-08)
→ 雛形への提案: `src/core/` に「状態を文字で返す」「意味単位の操作を受ける」口を置く(research/2026-10-07-ai-game-factories.md の候補と同じ)。
- **同じ結論の業務での例**(CEDEC KYUSHU、ファイナルファンタジー ピクセルリマスターの LLM による QA 自動化): ①実行役の AI に「何を確かめるか(期待値)」を見せず、判定は別の AI に任せる(思い込みで「確かめた」と言うのを防ぐ)②AI は「どこへ行くか」だけ決め、道順は経路探索の計算に任せる ③位置・通れるマスは画像でなく JSON で渡す ④仕様書から画面遷移と大事な変数を抜き出して渡す。うちの `core/probe.ts`(状態を文字で・意味単位の操作)と ①〜③ が一致。①は雛形にまだ無い(bot の判定は sim の表を人が読む)。

## 7. 細かく縛るより目的を一言で(脆弱性の研究の紹介より)

- 稼働中の AI 製 Web アプリ 200 件の 91% に脆弱性(論文 "Understanding the (In)Security of Vibe-Coded Applications"、ITmedia 10/7 報道)
- やり直し時の再発率: 工夫なし 25.7% / **「本番運用に耐えるものを」と一言 11.0%** / セキュリティ用スキル追加 11.9% / **細かい技術指示 45.7%**
- 上位モデルに替えてもほぼ改善しない
- 公開前に 5 項目を見る: 認証・認可 / 秘密情報 / 入力 / DB の権限 / 依存パッケージ。**作った会話とは別の会話で**認可の抜けをレビューさせる

**効く理由**: 細かい指示はモデルの判断を狭め、書かれていない所が手薄になる。目的を言えば全体に気を配る。
注意: 対象は Web アプリ。ゲームにどこまで当てはまるかは未確認。数字は報道経由で原論文は未確認。紹介記事の筆者は自社診断サービスの宣伝つき。
5 の「4 つの決まり」とは矛盾しない(範囲と報告を決めるのが 5、作り方を細かく縛らないのが 7)。
出典: https://qiita.com/bpr_prot/items/2ab4435eadadf932d3fb (2026-10-07、確認 2026-10-08)

## 8. 画面レイアウトはスライドで人が直し、スクリプトで書き戻す(非公開の企画 repo より、2026-10-08)

- 画面の定義(JSON)から、1 画面 × 1 案ずつスライドに図形で描く。デザイナーはスライド上で移動・大きさ・文字・追加・削除をする
- スクリプトで読み戻し、変更を「どこから来た要素か」(部品の上書き / 状況ごとの上書き・追加・削除)ごとに定義へ書き戻す。前回の状態は控えのファイルに持つ
- 1 ファイルにまとめ、1 ページ目に全ページへのリンク目次。見出しはスライドのタイトル枠に入れる(枠の外に置くと余白の原因になり、目次にも名前が出ない)

- **Figma 版も同じ往復で動いた**(2026-10-16 仕事の案件): 定義 → プラグインで全画面を作る(1 枚目に目次・各ページに「目次へ」、仮絵は重ねて隠す/出すを切り替え)→ プラグインで配置を JSON に書き出し → スクリプトで定義に戻す。罠は env-gotchas の Figma 節

**効く理由**: 人は慣れた道具(スライド)で直せて、AI は定義ファイルだけを正本として扱える。往復しても定義が壊れない。

## 9. 長くなったセッションは、圧縮より「新しいセッションに引き継ぐ」(非公開の企画 repo と会議室の 2 代目交代より、2026-10-13)

- **区切る合図**(どれか 1 つ): 話題が何度も変わった / 往復が多い / 大きな作業が一段落した。Claude の方から「ここで新しいセッションにしましょう」と勧める。自動の圧縮は、細かい決めごとが落ちやすい。
- **引き継ぐ前に Claude がやる 3 つ**:
  1. 作品の repo の申し送り(HANDOFF.md、作品によっては docs/ の再開用メモ)の先頭に「やったこと / 次にやる順番 / 返事待ち / 道具の使い方」を書く
  2. 次のセッションでも要る手順を、メモリ(PC の Claude Code)か repo の文書に残す
  3. commit・push する
- **新しいセッションの始め方**(どちらかを Claude が出す):
  - PC のデスクトップアプリ: 申し送りの指示を入れた「タスクの提案」(spawn_task)。ただし別の作業コピー(worktree)で始まる。または、いつものフォルダで新しいセッションを開き、Claude が用意した 1 行の指示を貼る
  - クラウドのセッション: Claude が create_session で新しいセッションを直接立てられる(会議室は 10/13 におばけ提灯の調整をこの方法で渡した)
- **名前**は「<セッション名>(N代目)」にそろえる。前の代は消さずに残し、記録に無いことだけ聞く(会議室の 1 代目→2 代目と同じ)。

**効く理由**: 長い会話は前半の決めごとほど薄れる。申し送りをファイルに書かせると、次の代も、別の AI も、同じ所から始められる。
**圧縮か新しいセッションか**(調べた結果 `research/2026-10-13-compact-vs-new-session.md`、公式ドキュメントより): 同じ作業の途中で流れが良いなら圧縮(`/compact <残すもの>`)。作業が変わった時・同じ直しを 2 回した時・別の PC や AI が引き継ぐ時は、申し送りを書いてから新しいセッション。圧縮で落ちるのは会話の中だけで言った指示・ツールの出力・数値や理由の細部。ルートの CLAUDE.md とメモリは読み直される。
**雛形に入れた(2026-10-13、Mukkii「普遍的に効くなら指示に入れてよい」)**: ①圧縮・/clear のあとに HANDOFF.md を自動で読み直すフック(`.claude/settings.json` の SessionStart)②CLAUDE.md の「Compact Instructions」(残すもの)③AGENTS.md 6 に 1 行(作業が変わったら新しいセッションを勧める)。使用率で自動に新しいセッションへ移る公式の方法は無い。

- 追記(2026-10-16 仕事の案件): **申し送りは再開メモの最上段に新しい順で積む**(やったこと / 次の順番 / 返事待ちの番号(新代が最初に聞く)/ 関係するセッション名 / ツールの作り直しコマンド)。新セッションへの合図は「(repo)の続き。<再開メモ> を読んで現状把握して」の 1 行。
- **切る基準 4 つ**: A 話題が変わる / B 大量の調査ログを取り込んだ直後 / C 同じテーマで往復 20 回超 / D 機械作業だけが続くなら切らずに Sonnet へ切替。提案は再開点とセットで。実測: サブエージェントの調査 1 回で 40〜60 万トークン。LLM を使わない取得スクリプト・機械作業の Sonnet 化・サブエージェントは 2〜3 体に絞る、が効いた。

## 10. 全要素のモックを一晩で揃える(非公開の作品 2 本より、2026-10-13)
- **デモ固定ルート**: 設定で ON にすると、乱数の種・出会う敵・報酬を固定し、ランダムでは会えない要素にも順番に必ず出会う。このルートを最後まで通す自動テストを置けば「全部入っている」を機械で確かめられる。
- 作りかけの物は、画面か札の文に「ハリボテ」と出す(見た人が完成品と誤解しない)。
- 専門のセッションに分担させる時は、つなぎ口(データの形・呼び出し方)の約束を先に決める。
- 版権ものは、ID に原作の名前を入れず役割の語にする(`guest_`、`town_a_` など)。表示の文字列はそのまま。監修や公開の前に名前を差し替えやすい。
- **別のセッションに中身を作らせる時は、書き方を先に提案して合意してから**作ってもらう。合意前に作ると、つなぎの検査で何十件も誤りになる(2026-10-14)。
- 監修や確認用の画面写真は、デモ固定ルートに乗って自動で撮る(例: 26 画面を 1920×1080)。音量・設定・記録は控えから戻す。
- 外に出す版と社内の版は 1 つの元から書き出す。社内だけの列(見積もり等)は書き出す時に自動で外す。人が手直しした提出版を正とし、印を付けた時だけ上書きする。
- 試遊版を配る時は、タイトル画面に版名を出す。感想は「版・どこ・何をしたら・どうなった(期待)・重さ」の 1 行で集める。プレイデータの送信は既定で切る。
- プログラマに渡すデータには、JSON Schema と、検証付きの書き出し道具を付ける。

- 追記(2026-10-16 仕事の案件): **自動再生(デモ)の段の機械**は、戦闘外でも進む段を番号の範囲でなく明示リストで持つ(無いと敵全滅の瞬間に無音で永久停止、3 回再発)。一定時間進まなければ警告して強制で通す見張りと、仕掛けごとの 1 行ログ、ループ全体の try/catch。

## 11. 曲のオマージュを安全に作る(ImoteControllDandy より、2026-10-14)
- 借りてよい: コード進行・構成・テンポ・楽器編成。借りない: メロディ・歌詞・リフ。
- 似すぎの確認は、移調しても変わらない「音程の動き + リズム」で比べる。8 音以上一致なら書き直し、5〜7 音は要注意。結果は記録に残す。
- 曲調の指示に作品名・作曲者名を入れない。
- **サブエージェントで並列に作る時は、ブランチを分けるより「触ってよいファイルを分ける + git は司令塔だけ + 境目の関数を先にスタブで置く」**が速い。4 パートが約 15 分で終わり、ぶつかったのは ID の重複だけ(2026-10-15 game-creator-life)。
- デモ固定ルートでも、地図に「選べない・暗い・光らない」見せるだけの分かれ道を描くと 1 本道に見えない(2026-10-15)。
- 数値を 3 か所(コードの既定値・同梱 JSON・外部 JSON)に持たない。登録表 1 本にして、実験用のファイルだけで上書きする(2026-10-15)。
- **bot の 1 周分のログを文字で吐いて通読し、同じ文の回数を数える**。画面で 5 周するより速く、同じ小ネタの連発や「一度も起きない終わり方」が数字で見つかる(2026-10-15 game-creator-life)。
- 同じ repo に司令塔のセッションを 2 つ立てない。新しく立てる前に、前のセッションを止めて(会議室は archive まで)、`git fetch` で origin/main を読んでから始める。2 つ立って片方の作業が丸ごと無駄になった(2026-10-15)。


## 12. AI で 3D を作る流れ: 絵で完成形 → 素材を仕分け → 組み立て → 別の AI が多視点で見比べる(外部の公開事例、2026-10-16)
- 出典: Sac 氏「Opus 5.5 / Astra + Tripo で 3D ゲーム」(X 記事 2026-10-15、16 日で制作。Tripo の紹介リンク付きの記事なので Tripo 推しは割り引く。コードは翌週 GitHub で公開予定)。Unity 版だが流れはブラウザ(Three.js / Babylon.js)でも同じ。
1. **完成形を先に絵で決める。** 画像生成で場面の 1 枚を決めてから、俯瞰(配置)・斜め(高さ・形)・細部を同じ絵柄で足す。キャラは T ポーズの四面図(正・側・背・斜め)を揃える。
2. **素材ごとに作り方を仕分けさせる。** 参考画像を AI に見せ「3D 生成(Tripo 等)で作るもの / Blender・コードで組むもの」に分けさせ、画像に印を付けて人間が確認。
3. **組み立ては参考画像と生成した素材を一緒に渡す。** 「参考画像どおりに再現」と頼む。
4. **見た目の確認も AI に。** 組み終わったら**別の AI(作った本人ではない)**に、複数のカメラ位置から撮った画面と参考画像を見比べさせ、違いが無くなるまで直させる(盲審)。会議室の「自動スクショ」(§10)の 3D 版。
5. キャラの骨と動き: 四面図 → 3D 生成(Tripo Smart Mesh P2.0 = 面数を抑えて骨入れしやすい)→ 骨入れ(Auto-Rig Pro、有料の Blender 拡張)→ 基本の動きは Mixamo → 道具を握るなど細かい動きは Blender の IK で直させる。
- 会議室の当て方: 3D の作品では最初の 1 時間で 1・2 を済ませ、参考画像を `docs/look/` に置いて「見比べ係」のサブエージェントに渡す。2D でも「完成形の 1 枚を先に作る」は効く(topics/06-assets.md のスタイル定義と同じ考え)。

## 13. 大きな仕様書を AI と一緒にまとめる(仕事の案件から回収・一般化、2026-10-16)
- **正本表を 1 枚**: 「正本のファイル / 人間用の置き場(スプシ・Drive)/ 作り直しコマンド」を表にして再開メモの先頭近くに置く。生成物は手で直さない。
- **裁定は凍結ではない**: 実機と仕様が食い違っても「違反」と決めつけず、改定か事故かをまず本人に聞く。改定なら裁定を更新し、依存する計算をやり直し、古い裁定での机上の結論は捨てる(研究側が「違反だから戻す」として 1 回失敗)。
- **案は切り替えで実機に入れる**: 提案段階の数値は既定を変えず、切替パネルの選択肢として入れる(1 点に固定すると案の優劣に数値の差が混ざる)。捨てた案は消す。
- **数値は 4 層に重ねる**: 原作の既定 → 本作の差分 → 案ごとの実験 → その場の調整。「本作の差分」を外せば原作に戻る(雛形の tuning.ts と同じ考え)。
- **AI 向けの仕様はテストの形で**: 「前提 → 操作 → 期待(数値)→ 参照」。ID は欠番可・付け替え禁止。未確定は「★要検証」で skip。乱数は系統別に注入して固定でき、統計テストは試行回数と許容幅を書く。ルールの説明は 1 か所にして参照だけにする。
- **原作のある作品は「再現」と「差分」を別ファイル**: まず原作をそのまま動かし(ルールの誤解を新要素と混ぜずに潰す)、差分をスイッチで載せる。
- **IP に依存しない作り**: 役割(機能)と表現を分け、固有名は語彙表の CSV 1 つに。ID は役割語。一度混ざると設計がその IP に寄って汎用性を失う。数値は原作の桁に揃えた整数(割合・枚数・コスト・ターンは倍にしない)。
- **並列で書く時の契約を 1 枚に**: 担当ファイル以外を書かない / commit・push・ビルドを走らせない(出力の取り合い)/ 登録表は統合担当だけ / 公開メソッドの名前と引数を変えない / データの未知の欄はローダがエラーにする / ファイルがまだ無ければ 0 件でログを出して続行。
- **2 セッションの分担は「対象」で切る**(番号帯や役割で切ると破綻)。排他は物理境界(repo・フォルダ)だけ。共有ファイルは節の見出しに所有者を書く。数値の最終決定は人間。「数値を 1 つ動かす → ビルド → 触る」が数分のループになったら 2 つを合体する。
- **遊び比べ**: 5 案を比べる時、比べどころは 3 つ・遊んだ後の問いは 3 問だけ。戦闘ごとに CSV へ自動記録し、数字にならないものだけ人に聞く。未実装の組み合わせは画面に赤字。
- **現役の資料だけを人に見せる**: 索引で★の付いたものだけ共有ドライブへ同期し、旧案は archive/ に移す(消さず要約を 1 本)。人間用の「ざっくり版」と AI 用の「詳細版」を分ける。
- 世代交代と切り替えの基準は §9 の追記。表の書式は knowledge/sheet-style.md。
- **「概要書の絵 × モックの写真」の食い違いは AI に仮の裁定で仕分けさせる**(2026-10-16): 107 件を「今やる / 後で / 済(写真で確認)/ 見送り / デザイナー待ち / 仕様待ち」に分け、理由・難しさ・直し方の手がかり(どのクラス・どの数値)を 1 行ずつ。同じ直しで消える行はまとめる(22 件 → 実作業 16)。表には「AI 仮」と色で示し、人は裁定だけ見る。「今やる」は同じ日にモックへ入った。
- **仮絵の受け渡し**: 生成 AI で作った仮絵は共有ドライブの決まった場所に、スクリプトで一覧 CSV(ID・使う画面・元の生成手段)と「はじめに」をつけて置く。デザイナーは一覧から差し替える。
- **長い原作資料(PDF 等)の読み取り**は、読み取りの指示書を 1 枚作って複数のエージェントに分けると安く速い。上限(429)に当たるので、再開できる単位で出力させる。スプシへの書き込みは「成功を確かめてから元を消す」(GAS が不安定)。

## 14. トークンを抑える(作品の司令塔から、2026-10-16 実測)
- **一番高いのは AI の読み手(ペルソナの通読)に長い記録を読ませること**。Opus の読み手 2 人 × 約 10 万トークン/回 を 60 回近く回していた。
- 読み手の指摘の半分以上は「状態と本文の食い違い」(独立中に会社の話・海外で国内の話・子の年齢・同じ年に 2 社 等)と「同じ文の繰り返し」で、**規則にすれば機械で数えられる**。→ 描画なしで回して状態と文を照らす点検(作品で 30 組約 25 秒、AI 不使用)。雛形に `npm run audit`(規則は `src/game/audit.ts`)を入れた。年の途中で状態が変わる行は誤検知になるので、前と後の両方で合わない時だけ数える。
- 回し方: ① audit で件数の多い規則から直す ② AI の読み手は 1 回 1 人・安いモデル(Sonnet)で、観点を機械で分からないもの(笑い・意味不明な行・史実)だけに絞り、報告 500 字以内 ③ 読み手が見つけた機械で分かる矛盾は、直すたびに audit の規則に足す(回を重ねるほど AI に頼む量が減る)。
- 長い記録・大きな出力は司令塔が自分で読まず、サブエージェントに読ませて結論だけ受け取る。大きなツール出力は head / grep で絞る。
- 決まった直しの繰り返しは、司令塔のモデルを Sonnet に落とす(仕組みの大改造の時だけ Opus)。
- 2 つのセッションが同じ記録を読むと二重払い。片方は機械の点検とコード、もう片方は「平板な行の書き直し」だけ、のように読む物を分ける。

## 15. 単発の HTML を公開する(会議室が引き受ける、2026-10-17)
- どのセッション(claude.ai のチャット含む)で作っても、**公開は会議室に「これを公開して」と HTML と og 画像を渡す**。会議室の決まりを知らないセッションは Netlify などを勝手に選ぶ(10/16 に実例)。
- 会議室の手順(人の手なし、約 5 分): ai-ops「Bootstrap Web Repository」で repo → 「Enable Claude」で鍵 → `site/index.html`・`site/ogp.png` を置き、og:url / og:image を `https://<repo>.mucky-totoro.workers.dev/` に書き換え → `wrangler.jsonc` の assets を `./site`、deploy-cloudflare.yml のビルドを外す、Pages の build-and-deploy は手動だけに → push。
- 会議室のセッションからは *.workers.dev に curl が届かない(許可リスト外)。公開の確かめは Mucky Reader の read_web で読む。
