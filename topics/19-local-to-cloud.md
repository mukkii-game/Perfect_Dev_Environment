# ローカルのセッションをクラウドへ移す(検討中、2026-10-16〜)

Mukkii の意図: PC のローカル(Remote Control)で動いている作品・仕事のセッションを、クラウドのセッションに移して、どこからでも続けられるようにする。

## なぜ
- PC の claude が止まると Remote Control のセッションは夜中にまとめてアーカイブされる(env-gotchas、10/14・10/16 に実例)。
- クラウドなら PC を切っても続く。会議室の見回り(毎朝・毎晩)からも見える。

## 移す前に確かめること(作品ごと)
1. **作業中の変更が全部 push されているか**。ローカルの未コミット(is_dirty)は クラウドに来ない。移す前に PC で commit・push。
2. **repo の外に置いている物**: ゲーム本体・ローカルの道具(ffmpeg・JDK・Maven)・Google Drive のファイル。クラウドに無いものは、(a) セットアップスクリプトで入れる(JDK・Maven は apt / zip で入る)(b) 公開できない物はクラウドに置かない。
3. **既存ゲームの MOD**: ビルドに要るゲーム本体の jar(Steam で買ったもの)は再配布できないので repo に置かない。クラウドでは「仕様・コードを書く・単体テスト」まで、**ビルドと実機の確認・録画は PC**、と分けるのが現実的(要検討)。
4. **秘密の鍵**: 環境の network secrets か GitHub の secrets に置く。repo やチャットに書かない。
5. 必要なサイトが許可リストにあるか(knowledge/cloud-allowlist.md)。
6. 引き継ぎ: ローカルのセッションの最後に HANDOFF.md を書かせて push → クラウドで新しいセッションを同じ repo で立て、HANDOFF から再開(長い会話は持ち越さない。process-patterns §9)。

## 順番の案
- 仕様をまとめる仕事(スプレッドシートと md が中心)→ 移しやすい。先に移す。
- MOD のコード → 書くのはクラウド、ビルド・実機確認は PC の 2 本立てを試す。
- 個人の作品は雛形どおりなら、もうクラウドで動く。

## 未決
- MOD のビルドをクラウドでどこまでやるか(ゲームの jar をどう扱うか)。
- 移す作業は会議室がやるか、各セッションに頼むか(案: 会議室が手順を渡し、各セッションが HANDOFF を書いて push、会議室がクラウドのセッションを立てる)。
