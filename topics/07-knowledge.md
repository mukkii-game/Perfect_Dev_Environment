## 知見の蓄積と活用(2026-09-15、設計を確定に近づける)

ユーザー提起: 開発中に得た知見(例: itch.io でスマホ版が動かない原因と解決、スマホで重い時の対処)を、世の中の TIPS と合わせて蓄積し、次からの AI 駆動開発で使いたい。懸念は「毎回読ませると重くならないか」。

### 答え: 3 層に分ければ重くならない

**2026-09-22 改訂: 0 層(コード)を足した。** 下の 3 層の上に、もう 1 段ある。

| 層 | 中身 | いつ読まれるか | 分量の上限 |
|---|---|---|---|
| **0 コード** | 知見を実装として固めたもの(`src/core/`)。自分用エンジン | **読まれない。使われるだけ** | 無制限 |
| **1 必読** | 「知らないと必ず踏む」落とし穴だけ。AGENTS.md の中に直書き | **毎回**(常に文脈に載る) | **15 行厳守**。増やすなら何かを 2 層へ落とす |
| **2 スキル** | テーマ別の SKILL.md(例 `mobile-web-perf`, `itch-embed`, `audio-unlock`)。説明文に発動条件を書く | **関連する作業の時だけ**自動で読まれる | 1 本 100 行程度。10〜20 本 |
| **3 書庫** | 生の知見カード。日付・現象・原因・解決・出典 | **困った時に grep される**だけ | 無制限 |

- 重さの正体は 1 層だけ。2 層は「スマホ対応で困った時」にしか読まれず、3 層は検索した数件しか読まれない。**だから増やしても普段のトークンは増えない。**
- 1 層の例(実際に入れる候補): 「itch.io の埋め込みで動かない時はまず ◯◯」「iOS Safari は最初のタップまで音が鳴らない」「`base` は `./`」など、**毎回必ず効く 5〜10 個だけ**。

### 集め方(2 経路、どちらも自動)

1. **自分の開発から**: 作品 repo の `HANDOFF.md` に「今回ハマったこと」欄を設ける(AGENTS.md に明記)。週次 Routine が全作品の HANDOFF を読み、新しい知見を 3 層に転記。3 回以上出てきたテーマは 2 層(スキル)に昇格、毎回踏むものは 1 層へ。
2. **世の中から**: gd-knowledge の収集レイヤー(Actions で RSS・記事を無人収集)と同じ型を「Web ゲーム開発 TIPS」用に 1 本作る。AI モデルの癖(→ 06・03)も同じ仕組みに乗せる。

### 置き場

- 実体は `dev-knowledge` repo(private)。作品 repo からは **スキルだけ**をコピー or サブモジュールで持ち込む(3 層は持ち込まない)。
- 人間が読む一覧はスプシ(検索・並べ替えが楽)。md が正本、スプシはミラー。

### 収集レイヤーの副次的な利点(2026-09-15 に判明)
- 会議室セッションの実行環境は egress 制限があり、読めない外部サイトがある(例: blog.toripota.com)。
- **GitHub Actions 上の収集スクリプトには同じ制限がない**ので、「会議室が読めなかった URL」を `research/_to_fetch.txt` に積み、収集 Routine が取得して知見カードにする経路を作る。

## スキルを並べすぎる罠(2026-09-22・OpenAI の記事を受けて是正)

| 記事の指摘 | うちの状態 |
|---|---|

| 段階的な開示(入口は案内板にする) | **設計だけあって未適用**。3 層(必読/スキル/書庫)を自分で決めておきながら、書庫に置くべきものをスキル層に置いていた |

| 完了の定義を先に与える・止まらせない | **先回りできていた**。AGENTS.md 冒頭 3 行がそれ(ユーザーの 9/13 の指示が元) |

**是正**: Phaser 29 本を `docs/phaser/reference/` へ降ろし、入口スキル 1 枚に置き換えた
(web-app-template)。内容は消していない。題目を探して 1 枚だけ開く形。

**運用の規律として決めたこと**:
1. `AGENTS.md` は **50 行を上限**。足したければ先に 1 行削る。削れないなら足さない。
2. 区別する。**事実の記録**(台帳・gotchas)は安い(必要時に grep するだけ)。**AI への指示**は高い
   (毎回読むので全作品の全セッションに課税される)。事故のたびに後者へ足す癖を止める。
3. 半年ごと、または大きなモデル更新のたびに、AGENTS.md の各行へ「今のモデルでも要るか」を問う。
   これは topics/10 の Lv6「先読みできる」の実践そのもの。

**次に見るべき所**: 権限 3 ゾーンの書き方。「ゾーン A(ゲーム repo 内)では確認不要」を
明示しないと、賢いモデルほど安全側に倒れて止まる。11 と合わせて直す。

### 上限の数字について(2026-09-22 追記・訂正)

最初に「50 行」と言ったが、**これは根拠のない数字で、私がその場で決めたもの**。
しかも守るために害のない行を削っていた。ユーザーの「世の優れた使い手を参考にしているのか」
という問いで検証したところ、参考にしていなかった。調べ直した結果:

| 出典 | 推奨 |
|---|---|
| Anthropic 公式(claude-code-best-practices) | 数値を出さない。「簡潔に、具体的に」 |
| 実務者のブログ各種 | 150〜250 行以下が多数派。理想 100 行以下、60 行以下の例もあり |
| よく挙がる劣化の目安 | 80 行あたりからルールが落ち始め、200 行超で塊ごと無視される |

**うちの 53 行は相場から見て軽い方**で、心配する水準ではなかった。数字を 100 行目安に緩め、
削った行は戻した。ただしブログが出典の数字であり、公式が保証した閾値ではない。

**本当の基準は行数ではない**:
1. モデルが自力で分からないことか(分かることは書かない)
2. 無くて実際に困ったことがあるか(想像で足さない)
3. 毎回読ませる必要があるか、場面を指定して参照させれば足りるか

**教訓**: 数字は分かりやすいので、根拠がなくても決めたくなる。決める時は出所を言う。
言えないなら「今これだけあるから増やすな」と正直に言う。


## 0 層(コード)を足した理由と、実際に持ち出した記録(2026-09-22)

ユーザー提起: 「ジャンルごとの基礎ノウハウは skill で集めるか、マイノウハウに貯めるか、
自分用エンジンとして保全するか」。

### 答え: 3 つとも要る。ただし優先順位は逆で、**コードが最優先**

新しい知見が出たら、まず **「コードにできるか」**を問う。

- できる → `src/core/` に実装する。例: 「iOS Safari は最初のタップまで音が鳴らない」は
  `audio.ts` に解放処理が入っていれば、知識として持つ必要すらない。
  **読まれない・間違えられない・トークンを食わない。文章より常に強い。**
- できない → 文章にする。外部サービスの仕様(itch.io はモバイルで必ず Run game ボタンが出る、
  butler の channel push は build を積む)はコードで吸収できないので文章で持つしかない。
- 文章のうち、特定作業の時だけ要るものを **skill** にする。
  **skill は目的ではなく、文章を必要な時だけ読ませるための仕掛け**。「skill を集める」は発想がズレている。

### 実測: ノウハウは溜まっていなかった

| 場所 | 中身 | 状態 |
|---|---|---|
| `gd-knowledge` | 世の中のゲームデザイン知識 4,615 ファイル / 79MB | 毎朝自動で稼働中 |
| 会議室 `knowledge/env-gotchas.md` | 環境の地雷 21 行 | 会議室の中だけ |
| `tetrishoot/docs/WEB-GAME-RULES.md` | ブラウザゲーム共通ルール 328 行 | **1 作品に埋もれていた** |
| `tetrishoot/docs/ITCH-MOBILE.md` | itch.io × iPhone 実践ノート 1,237 行 | **同上** |

前者 2 本の見出しには**「持ち出し用」**と書いてあり、1 年近く持ち出されていなかった。
ITCH-MOBILE には **「2-2. 答えは隣の作品が持っていた」** という節すらある。
入力の多重登録の答えが自分の別作品に既にあったのに気づかず溶かした記録で、
**これが「溜めていない」ことの実費**。

### 実施

`web-app-template` へ運んだ(2026-09-22):
- `docs/knowledge/` に 2 本(3 層=書庫)
- `.claude/skills/web-game-trouble/`(2 層)。発動条件は「スマホや itch.io で動かない時」に限定
- `AGENTS.md` に必読 4 行(1 層): window だけに付けるな / キャッシュを疑え / 画面に数字を出せ / 逆引き表の場所

### 残っている宿題(次にやる)

**0 層への昇格がまだ。** WEB-GAME-RULES の「入力 6 系統登録 + 重複排除 + capture」は、
本来 328 行の説明文ではなく 60 行の `src/core/input.ts` であるべきもの。
現在の雛形の `input.ts`(61 行)は Phaser の入力機構に素直に乗っているだけで、
iframe 埋め込みでの取りこぼし対策が入っていない。**ただし実機で確認せずに移植すると、
直った気になって壊れる**(まさに ITCH-MOBILE が警告している失敗の型)。
実機で触れる時にまとめてやる。

### 運用として決めたこと

- 作品で「ハマった」ことは、その repo の `HANDOFF.md` に書く(雛形の作法)。
- 週次レビューが全作品の HANDOFF を読み、**まず 0 層にできるかを問い**、
  できなければ 3 層へ。3 回出たテーマは 2 層へ、毎回踏むものは 1 層へ。
