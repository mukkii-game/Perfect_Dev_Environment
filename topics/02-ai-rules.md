# 02 全 AI 共通の作法(agent.md 系)

## 現状の結論(推奨案、未確定)

**正本は 1 つ、入口は AI ごと。**

```
AI_RULES.md      ← 正本。全 AI が読む共通の作法
CLAUDE.md        ← 「AI_RULES.md を読め」+ Claude 固有の 2〜3 行
AGENTS.md        ← 同上(Codex / Cursor / 汎用)
GEMINI.md        ← 同上(Gemini CLI)
```

AI_RULES.md に入れる内容(章立て案):

1. **このプロジェクトは何か**: SPEC.md を読め。ジャンル別の追加指示は `rules/<genre>.md` を読め(例: `rules/puzzle.md`, `rules/3d.md`)
2. **作業の型**: まず動くモックを最短で。複数案を求められたら `variants/a`, `variants/b` に並べる。完成より公開優先
3. **技術の既定値**: 2D は Phaser 3、3D は Three.js、エンジンは `dev-engine` を使う。ビルドは Vite。TypeScript 可だが型で止まるな
4. **素材**: 自作より外部素材優先。クレジット不要のものを優先し、`ASSETS.md` に出典とライセンスを必ず書く。自動生成した場合はどの AI で作ったかも書く
5. **公開**: `docs/PUBLISH.md` を日英で埋めてから公開ジョブを叩く
6. **道具**: 検索・一括処理は `dev-tools` のスクリプトを使え(例: `tools/search.py`)。自前で同じものを作るな
7. **記録**: 汎用的に使える道具ができたら `dev-tools` に出す PR を提案する。環境の説明(STATUS 等)に影響する変更をしたら書き換える
8. **禁止**: テストのスキップ、ライセンス不明素材の使用、秘密情報のコミット

**書き方の原則**(モデル進化への対応): 細かく書きすぎない。「何を」「なぜ」を書き、「どうやって」は AI に任せる。モデルごとの癖は `knowledge/ai-models.md`(→ 07)に日付つきで置き、AI_RULES.md には入れない。

## 2026-09-13 追記(Q&A と方針修正)

- **GEMINI.md は要るか(Q)**: 既定では Claude は `CLAUDE.md`、Codex / Cursor / 多くのツールは `AGENTS.md`、Gemini CLI は `GEMINI.md` を読む。ただし Claude は `@AGENTS.md` の 1 行で取り込め(web-app-template が既にそうしている)、Gemini CLI は設定 `contextFileName` で読むファイル名を `AGENTS.md` に変えられる。**結論: 正本は `AGENTS.md` 1 本。`CLAUDE.md` は `@AGENTS.md` の 1 行。`GEMINI.md` は置かず Gemini 側の設定で AGENTS.md を読ませる。** 先の「AI_RULES.md」案は取り下げ。
- **自律の度合い(修正)**: 「SPEC 承認と公開承認の 2 点だけ」は誤り。人間も考える。正しくは:
  1. 人間の企画を **止めずにゴールまで作り切る**(だめもとで良い)。少し進んで確認、を繰り返さない。
  2. ただし「バーチャロンみたいなの」と言われたら、そっくりを完成させるのが目的ではなく **改造の土台**を作るのが目的。ゴール到達後は人間の指示で改善・変更・複数パターン出し(イテレーション)。
  3. 人間は本業の隙間に指示と回答をする。AI の質問は **作業を止めずに溜めておき**、人間が後でまとめて答える(GitHub Issue のコメントや PR 本文に「未確認事項」として並べる)。
  4. **5 本並行**で作れる体制。作品ごとにセッション / repo が独立しているので、会議室が 5 つの子セッションを持ち、人間は「次の指示を待っているもの」一覧だけを見る。
- **Yasu の教訓(セッション session_013QYmJuNe564wCoQgPScjHX)**: パイロット版に製品級の検査を掛けない。md と文脈を肥大化させない。Codex をクラウド共通化しない。詳細は research/2026-09-13-existing-infra-inventory.md。

## 実行部隊への発注の作法(2026-09-14 教訓)

- 子セッションは人間が見ていないので、**許可プロンプトが出た時点で止まる**。発注文に必ず「npx -y や任意 URL の curl は禁止、git clone / npm ci / node に限る、迂回できないものは HANDOFF に人間の手順として書く」を入れる。
- 30 分ごとに commit・push させ、途中経過を会議室が読めるようにする。
- 会議室は子セッションの状態を定期確認し、REQUIRES_ACTION なら迂回指示で再起動する。
- **2 回目の教訓(2026-09-14)**: `git rm` のような削除も止まる。子セッションに向くのは「新規ファイルの作成と push だけ」の仕事。既存を消す・置き換える仕事は会議室(人間が見ているセッション)で直接やる。

## 検討中の論点

1. `.skill` / スキルの単位をどう切るか。候補: 「新作を生やす」「公開する」「素材を探す」「複数案を出す」「英語化する」。Claude は skills、Codex は AGENTS.md 内の手順、Gemini は GEMINI.md で同じ内容を読ませる。**同じ手順書を 3 形式に変換するスクリプト**を `dev-tools` に置く案。
2. Claude と Codex の統一: Yasu の結論は「無理にやらない」。GPT 側を使う時は ChatGPT のクラウド実行機能で、Codex にクラウド共通化ルールを課さない(ユーザー案)。ここで確定させる。
3. 人間の介入点をどこに置くか。案: SPEC 承認 → 公開承認 の 2 点のみ。それ以外は自律。
4. ルールの検証方法。雛形で実際に 1 本作らせ、どの AI でも同じ動きになるか試す。
